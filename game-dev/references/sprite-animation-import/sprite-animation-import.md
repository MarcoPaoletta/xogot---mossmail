# Reference: sprite animation import (2D spritesheets → SpriteFrames) + per-animation transform

Implementation twin of the Build-GDD pattern `sprite-animation-import.md`. This is the "how it is written"; the pattern is the "what must happen". Proven on Starling Episode 1 (Makko art, Godot 4.7): rock enemy, flying enemy, boss.

The delivery for each character is one **spritesheet PNG per animation** plus a **TexturePacker-style JSON** per sheet (frame rects, `frameTags`, `anchor` bottom-center). Only the PNGs go into the Godot project. The JSON is **not** imported as a project resource, but you **read it externally** to build the frames, because naive cell-size slicing is wrong here (see below).

## 1. Why not "add frames from sheet" by cell size

Godot's built-in sheet splitter wants horizontal/vertical counts. These sheets have a **2px margin, 4px separation, and a non-rectangular frame count** (e.g. 48 frames laid on a 7-wide grid = 6 full rows + 6 = one blank trailing cell). Cell-size slicing then yields 49 cells with a stray empty frame, or the wrong regions if the margin is ignored. The delivered JSON already has the **exact per-frame rectangle**, so use it.

## 2. Build one SpriteFrames per character from the JSON rects

For each character, for each animation sheet:

- Read the JSON, take the frames in numeric order (`..._000`, `..._001`, …), collect each `frame` rect `(x, y, w, h)`.
- Create one `AtlasTexture` per frame: `atlas` = the imported sheet `Texture2D`, `region` = `Rect2(x, y, w, h)`.
- Add them to a `SpriteFrames` animation named after the sheet (`idle`, `walk`, `attack`, `die`, `telegraph`, `fly`).
- Set the animation speed from the delivered frame `duration` (≈83ms → 12 fps).
- Set loop: **on** for `idle`/`walk`/`fly`; **off** for gating states (`attack`/`telegraph`/`take_damage`/`die`) so `animation_finished` fires and the FSM can exit them.
- `ResourceSaver.save()` the `SpriteFrames` to a `.tres` next to the sheets.

This mirrors the convention Godot itself uses when you build frames in the editor (one AtlasTexture sub-resource per frame). `scripts/build_spriteframes.gd` is a drop-in builder: fill its `DATA` dictionary (baked frame rects) and run it.

**⛔ Gate before building: verify the JSON matches the CURRENT PNG.** Sheets get re-generated by the art tool, and an old JSON's rects will not match a new PNG. For each sheet, confirm the JSON `meta.size` equals the PNG's real width×height before trusting its rects. A dimension mismatch means the JSON is stale, stop and re-pull it.

## 2b. Not every delivered frame ships: trim the dead ends

⭐ **The importer decides how many frames to keep, and it is expected to drop some.** Generated clips routinely arrive with dead frames on both ends: the subject holds still before the motion starts, and a tail of frames after it has already come to rest. Measured on Starling Episode 4 (11 Makko clips): one attack carried **9 dead frames at the tail**, another **7 at the head**, and two looping walks closed with a jump ~1.8x a normal step that a 3 frame trim cut to ~0.4x.

- **The trim is a frame range in the builder data (`from`, `to`), never an edited PNG and never a re-cut JSON.** The delivered art stays the source of truth, so a re-generated sheet cannot silently change what ships.
- **The cut rule is measurable:** drop a leading or trailing frame while it is visually identical to its neighbour, that is while nothing has moved yet or nothing is moving any more. Stop at the first frame where the pose changes.
- ⛔ **A wind up is not a dead frame.** Anticipation and telegraph frames are the contract with the player: the trim removes stillness, never a tell. When in doubt, keep the frame and say so in the report.
- **On a looping clip, the trim is also how you close the cycle.** If the last-to-first jump is much larger than the median step, walk the end frame back a few and measure again; pick the end that minimises the wrap. If no end improves it, the cycle itself is off, report it rather than forcing it.
- **Two invariants survive any trim:** the clip still ends in the pose the next state expects, and `animation_finished` still fires (loop stays off on every gating state).
- **Report the kept range per trimmed clip** (`headbutt: kept 4 to 21 of 48`), so the next session can tell a deliberate trim from a miscount.

## 3. Running the builder without an editor-script runner

If a full editor-script MCP (e.g. Fennara `run_scene_edit_script`) is up, run the build logic there. If it is not (godot-ai alone has no editor-script-run and no sheet-slicer op), run the builder **headlessly**:

1. Write the builder as a plain `Node` script (NOT `@tool` — a `@tool` `_ready` calling `get_tree().quit()` would quit the *editor* if the scene is ever opened) whose `_ready()` builds + saves the `.tres` then calls `get_tree().quit()`.
2. Put it on a one-node throwaway scene and `project_run` that scene. `ResourceSaver.save()` writes into `res://` (the project folder) when launched from the editor.
3. Read the game log for the per-character `err=0` lines, then `filesystem scan()` so the editor picks up the new `.tres`.
4. Assign each `.tres` to the character's `AnimatedSprite2D.sprite_frames`, set `animation` and `autoplay` to the resting state, and save the scene.
5. Delete the throwaway builder script + scene.

Verify by screenshotting the 2D viewport through the MCP (the sprite must render), never by desktop automation.

## 3b. Where the files live, and how verification is done (Starling Ep 1, Marco, 2026-07-23)

- **Only the PNG goes into the project.** The Makko export JSON is read externally to build the `SpriteFrames` and then stays as reference **outside** the project, in the collab tree (`Makko/_makko-json-ref/<creature>/<anim>.json`), never in `images/`.
- **Name the PNGs simply** (`idle.png`, `walk.png`, `attack.png`, `die.png`) and organise by world: `images/worlds/1 - Gloomlands/{enemies/<creature>/, boss/, environment/}`, with the player shared at `images/player/`.
- **Verify scale and offset with an MCP test scene, never by eyeballing one pose and NEVER with computer use.** Author a throwaway probe scene (prefix `_`) with one copy of the sprite per animation in a row, each autoplaying, over a baseline guide and a fixed height reference rect (that is what `scripts/calibration_harness.gd` in §5 packages). Run it and screenshot it through the Godot MCP, tune the resource, re-run, delete the probe after. Marco explicitly bans computer use and desktop automation on his PC: all verification stays inside the editor via the MCP.
- **This whole integration went to the GDD as spec, no code written ahead of the build** (`Starling - Build GDD Addendum (Player Animation Integration).pdf` plus `Starling - Player Animation Sizes (reference).png` in the Episode 1 folder): the build agent writes the code, the spec describes the behaviour, the exposed parameters and the acceptance criterion.

## 4. [MAKKO ONLY] Per-animation scale, offset, and native facing

Makko generates **each animation on its own canvas**, so within one character the frame size and aspect ratio differ per animation (Starling player: `attack` 516×302 landscape, `fall` 284×516 portrait, same character), and the subject sits at a different offset inside each frame. One `AnimatedSprite2D.scale` + zero offset makes the character change apparent size and jump position on every animation change.

Fix = a statically-typed **data resource holding a typed array of per-animation entries**, each entry a small struct of `anim` (StringName) + `scale` (Vector2) + `offset` (Vector2) + `native_faces_right` (bool), applied on animation change. `scripts/anim_frame_entry.gd` is the struct (one editable inspector row per animation); `scripts/anim_frame_transform.gd` holds the `Array[AnimFrameEntry]`, builds a name lookup, applies scale+offset on `animation_changed`, and exposes `faces_right(anim)` so the controller can set `flip_h`. Populate it by calibrating **each** entry against a fixed ground line and a target world height, one at a time. There is no single global scale that works.

This section does **not** apply to pixel-art or uniformly-exported characters (e.g. SpriteCook), whose animations share a canvas.

### 4a. The third datum: native facing per clip

Scale and offset are not the whole story. A Makko clip also has a **native facing**: which way its art points by default, before any flip. Do not assume every clip of a character faces the same way. On the Starling boss the four clips did not agree: `idle` faced **left**, while `walk`, `attack`, and `die` faced **right**. A single flip rule keyed on the actor's facing then made one clip point the wrong way.

The final flip must combine **two** facts: the desired facing toward the target AND the clip's own native facing. The rule, per clip, is equivalent to:

```gdscript
flip_h = (facing < 0) if native_faces_right else (facing > 0)
```

Store the native facing in the **per-clip entry** (next to scale and offset), read it through `AnimFrameTransform.faces_right(anim)`, and let the same rule cover every character. Carrying the datum in data removes the boss-specific `match` on animation name: the controller no longer special-cases which clips are mirrored.

### 4b. Resting animation must actually PLAY, not just be selected

A character can boot with `animation = "idle"` **selected but stopped**. A guard that only compares the animation NAME sees "already idle" and never calls `play()`, so the resting clip sits on frame zero and looks frozen. The fix is to call `play()` when the name differs **OR** when `not sprite.is_playing()`.

This is part of the contract, not an edge case: a resting state needs **real autoplay** on the `SpriteFrames`, or an explicit `play()` when the sprite is stopped. Selecting a clip is not the same as playing it.

## 5. Fast calibration: the visual harness

Calibrating scale/offset per animation by editing numbers blind is slow. `scripts/calibration_harness.gd` makes it fast: put it on a `Node2D` scene, assign the character's `SpriteFrames` (optionally an existing `AnimFrameTransform` to start from), and **run the scene**. Every animation plays side by side over one shared **ground line** and a **target-height bar**, so any animation whose feet leave the line or whose height is off is obvious at a glance, all at once instead of one pose at a time. Select an animation with the number keys and nudge its **offset** (arrow keys) and **scale** (`+`/`-`, `[`/`]` for fine) live; press **Enter** to print every entry as `anim / scale / offset` lines ready to paste into the `AnimFrameTransform`. This is the loop: run → see which are off → nudge → paste the numbers.

## 6. Reusable calibration procedure

Run this per character, and repeat step 9 per collision shape. It is the sequence proven on Starling (player, flying enemy, boss):

1. Open the harness with a ground line and a reference height.
2. Measure each clip separately. Do not copy one clip's numbers to another.
3. Adjust apparent scale first.
4. Adjust the feet / pivot offset second.
5. Verify in motion, not just on frame zero.
6. Test transitions between adjacent clips (idle to walk to attack and back).
7. Verify the scene's first frame (the autoplay clip on scene open).
8. Test both facings.
9. Recalibrate body, hurtbox, and hitbox separately from the sprite scale.
10. Store the values in data (the `AnimFrameTransform`), not in controller conditions.

## 7. Hard rules from Starling

These are the mistakes that actually happened, stated as rules:

- **(a) Scale and anchoring are DIFFERENT problems.** Enlarging does not fix a badly placed base. The Starling idle needed BOTH a scale bump (`0.4` → `0.5`) AND an offset change (`-256` → `-186`). With only the scale bump the body was the right size but still sat too high.
- **(b) Never compare raw scale numbers across clips with different canvases.** A landscape-canvas clip can carry a numerically larger scale without the body looking bigger. Starling `attack` at `0.8` versus `idle` at `0.5` is NOT "60% bigger": `attack`'s canvas is landscape, so the body fills less relative height. Compare apparent world height, not the scale field.
- **(c) Collisions do not scale blindly with the sprite.** When the flying enemy sprite grew 50%, the body radius went `52` → `70` and the hurt radius `64` → `82`, both less than a `1.5×` multiply. Recalibrate body, hurt, and hit shapes separately; do not multiply them by the sprite's scale factor.
- **(d) BAN multiplier phrasing without a baseline.** "Make it 1.75x bigger" is meaningless on its own. Require a target world height in pixels or a visual ratio against another actor. The boss's `0.875` reads two ways from the same number: `1.75 × 0.5` against the player baseline, OR just 25% over its own old `0.7`. State which baseline you mean.
